# 담당 반 학생이 Q&A를 올리면 교사 폰으로 알림 — 설계

작성일: 2026-09-03

## 배경

Q&A는 학생이 질문을 올려도 교사가 앱에 들어와야만 알 수 있다. 미답변 건수가 상단에
뜨긴 하지만, 그건 이미 들어온 사람에게만 보인다. 질문이 하루 이틀 방치되면 학생은
그동안 막힌 채로 있는다.

교사 폰으로 알림을 보내는 방법은 여럿이다. 카카오톡 알림톡, 웹 푸시, 문자, 이메일,
텔레그램 봇을 놓고 비교했다. **웹 푸시**로 정했다.

- 건당 비용이 없다. 알림톡·문자는 질문마다 돈이 나간다.
- 사업자 서류와 템플릿 사전 심사가 필요 없다. 알림톡은 영업일 2~5일이 먼저 든다.
- 질문 알림이 외부 메신저에 남지 않는다. 학생 이름이 카카오·텔레그램 서버를 거치지
  않고 우리 앱 안에서 끝난다.

공지사항의 "카카오 전송"은 아직 실제 발송이 아니다 (`Notices.jsx:192`가 `setTimeout`으로
성공한 척하는 자리표시자다). 즉 이 프로젝트에는 아직 어떤 알림 채널도 붙어 있지 않고,
이 작업이 첫 번째다.

### 웹 푸시를 고르면서 받아들인 위험

아이폰은 Safari에서 **홈 화면에 추가한 PWA**에서만 웹 알림을 허용한다(iOS 16.4+).
교사가 그 과정을 거쳐야 하고, 나중에 홈 화면에서 지우면 알림이 조용히 끊긴다.
교사 폰이 아이폰과 안드로이드가 섞여 있으므로 이 부담은 실제로 발생한다.

이 위험을 두 가지로 줄인다.

1. 아이폰에서 아직 홈 화면에 추가하지 않았으면 **토글 대신 방법을 안내**한다.
   토글을 눌러도 아무 일이 안 일어나는 상황을 만들지 않는다.
2. 발송이 실패한 구독(`404`/`410`)은 즉시 지운다. 죽은 구독을 남겨두면 "보냈다"는
   기록만 쌓이고 실제로는 아무도 못 받는 상태가 조용히 이어진다.

운영해 보고 아이폰 쪽 이탈이 잦으면 알림톡으로 갈아탈 수 있다. 알림 대상을 고르는
로직(아래 `notifyTargets`)은 채널과 분리해 두므로 그대로 재사용된다.

## 규칙

| 항목 | 결정 |
|------|------|
| 받는 사람 | 질문한 학생의 **담당 교사만**. 받을 교사를 못 찾으면(반 미배정이거나 반에 담당 교사가 없음) **관리자 전원** |
| 알림 내용 | 학생 이름 + 말머리까지. **질문 내용은 넣지 않는다** |
| 발송 시각 | 제한 없음. 새벽에 올라와도 바로 보낸다 |
| 알림 클릭 | Q&A **목록**을 연다 |
| 단위 | 사람이 아니라 **기기**. 교사가 폰과 PC에서 각각 켜면 둘 다 받는다 |

질문 내용을 빼는 이유는 알림이 잠금화면에 그대로 뜨기 때문이다. 교사가 카페나
지하철에서 폰을 꺼냈을 때 학생 질문이 옆 사람에게 읽히면 안 된다. 누가 급한지는
이름과 말머리만으로 판단할 수 있다.

특정 질문을 바로 여는 기능은 이번 범위에서 뺀다. `QnA.jsx`가 URL이 아니라 내부
`view` 상태로 화면을 전환하는 구조라 그것부터 손봐야 하고, 미답변 질문은 어차피
목록 상단에서 바로 보인다.

## 발송 경로

세 갈래를 놓고 비교했다.

| 방식 | 판단 |
|------|------|
| **Supabase 웹훅 → Vercel 함수** | **채택.** 질문이 어느 경로로 들어와도 반드시 발송된다. 기존 `api/*.js` 패턴 그대로라 새로 익힐 도구가 없다 |
| Supabase Edge Function | Deno 런타임과 `supabase` CLI 배포가 새로 들어온다. 관리할 배포 경로만 하나 늘고 얻는 게 없다 |
| 프론트에서 등록 후 호출 | 학생이 브라우저를 닫으면 유실된다. 발송을 학생 브라우저가 트리거하므로 누구나 가짜 알림을 쏠 수 있다 |

```
학생이 질문 등록
  → Supabase가 qna INSERT 감지
  → POST /api/notify-qna   (비밀 헤더 검증)
  → 질문한 학생 → 반 → 담당 교사  (반 미배정이면 관리자 전원)
  → 그 사람들의 기기별 구독으로 web-push 발송
  → 교사 폰에 "홍길동 · 내신과제"
```

## 구성 요소

### 1. PWA 기반 (신규)

지금 앱에는 매니페스트도 서비스 워커도 없다(`index.html`에 링크 없음, `public/`에 파일
없음). 아이폰은 이 둘이 있고 홈 화면에 추가된 상태에서만 알림을 허용한다.

| 파일 | 내용 |
|------|------|
| `public/manifest.json` | 앱 이름, 아이콘, `display: standalone`, 배경색은 기존 아이보리(`#F4F3EE`) |
| `public/sw.js` | `push` 이벤트 → 알림 표시, `notificationclick` → `/qna` 열기 |
| `index.html` | 매니페스트 링크 + `apple-touch-icon` 추가 |

매니페스트가 붙어도 학생 화면의 동작은 달라지지 않는다. 설치가 가능해질 뿐이다.

### 2. 구독 저장 (신규 테이블)

`docs/push-subscriptions.sql`

```sql
push_subscriptions
  id          bigint      생성 키
  profile_id  uuid        → profiles(id) on delete cascade
  endpoint    text        브라우저가 준 고유 주소 (unique)
  p256dh      text        암호화 키
  auth        text        암호화 키
  user_agent  text        "어느 기기인지" 화면에 보여주려고
  created_at  timestamptz
```

RLS는 본인 구독만 읽기·쓰기·삭제로 잠근다. 발송 함수는 서버에서 service role로 읽으므로
이 정책의 영향을 받지 않는다.

`endpoint`에 unique를 거는 이유: 같은 기기에서 알림을 껐다 켜면 같은 endpoint가 다시
온다. unique가 없으면 행이 쌓여 한 기기에 알림이 여러 번 간다.

### 3. 발송 함수 `api/notify-qna.js` (신규)

`api/check-wifi.js`처럼 **판단 로직을 순수 함수로 분리**해 테스트할 수 있게 만든다.

```js
notifyTargets(question, students, classes, admins)  // 누구에게 보낼지 (profile id 배열)
qnaNotification(student, question)                  // { title, body }
isDeadSubscription(statusCode)                      // 404·410이면 true
```

핸들러가 하는 일:

1. `x-webhook-secret` 헤더를 `QNA_WEBHOOK_SECRET`과 대조한다. 틀리면 401.
2. 웹훅 payload의 `record`에서 질문을 꺼낸다.
3. service role로 `students` / `classes` / 관리자 `profiles`를 읽어 대상을 고른다.
4. 대상들의 `push_subscriptions`를 모아 각각 발송한다.
5. 죽은 구독(`404`/`410`)은 그 행을 지운다.
6. 보낸 수·지운 수를 JSON으로 돌려준다.

한 구독의 발송이 실패해도 나머지는 계속 보낸다. 교사 한 명의 폰이 죽었다고 다른
교사가 못 받으면 안 된다.

### 4. 교사 화면 — 알림 켜기

Q&A 페이지 상단에 **"이 기기에서 알림 받기"** 토글을 둔다. "이 기기에서"라고 쓰는 건
실제로 기기 단위이기 때문이다. 교사가 PC에서 켜고 폰에서 안 켜면 폰은 조용하다.

상태별로 보여주는 것:

| 상황 | 화면 |
|------|------|
| 알림 켤 수 있음 | 토글 (끔/켬) |
| 이미 켬 | 토글 켜짐 + "이 기기로 알림을 받고 있습니다" |
| 아이폰인데 홈 화면 미추가 | 토글 대신 안내 — "공유 버튼 → 홈 화면에 추가 후 사용할 수 있습니다" |
| 브라우저가 웹 푸시 미지원 | 안내 문구만 |
| 권한을 거부한 상태 | "브라우저 설정에서 알림을 허용해 주세요" |

학생에게는 이 토글을 보여주지 않는다. 학생이 받을 알림이 아직 없다.

### 5. 환경변수

| 이름 | 위치 | 용도 |
|------|------|------|
| `VAPID_PUBLIC_KEY` | Vercel | 발송 시 서명 |
| `VAPID_PRIVATE_KEY` | Vercel | 발송 시 서명 (외부 노출 금지) |
| `VITE_VAPID_PUBLIC_KEY` | Vercel + 로컬 `.env` | 브라우저가 구독을 만들 때 필요 |
| `QNA_WEBHOOK_SECRET` | Vercel + Supabase 웹훅 헤더 | 아무나 발송 주소를 두드리지 못하게 |

`SUPABASE_SERVICE_ROLE_KEY`는 이미 Vercel에 있다 (계정 생성 함수들이 쓴다).

공개 키가 프론트와 서버 양쪽에 필요해서 이름이 둘로 갈린다. Vite는 `VITE_` 접두사가
붙은 값만 브라우저로 내보내기 때문이다. **같은 값을 넣어야 한다.**

## 테스트

자동 테스트로 덮는 것 (Vitest, 기존 방식 그대로):

- 담당 교사가 아닌 교사는 대상에서 빠진다
- 반이 배정되지 않은 학생의 질문은 관리자에게 간다
- 담당 교사가 없는 반이면 관리자에게 간다
- 알림 문구에 질문 내용이 들어가지 않는다 (잠금화면 노출 방지)
- 비밀 헤더가 없거나 틀리면 401
- 끊긴 구독(410)은 목록에서 제거된다

자동 테스트로 덮지 않는 것: 서비스 워커 동작, 실제 발송, 아이폰 홈 화면 추가 흐름.
이 셋은 배포 후 폰에서 직접 확인한다.

## 사람이 해야 하는 준비

코드만으로는 동작하지 않는다.

1. VAPID 키 생성 — `npx web-push generate-vapid-keys`
2. Vercel 환경변수 4개 등록 (위 표)
3. `docs/push-subscriptions.sql` 실행
4. Supabase에서 Database Webhook 등록 (`qna` INSERT → Vercel 주소, 비밀 헤더 포함)
5. 배포 후 교사 폰마다 한 번씩: 홈 화면 추가(아이폰) + 알림 켜기

**로컬에서는 확인할 수 없다.** 웹 푸시는 HTTPS를 요구하고, Supabase 웹훅이
`localhost`로 POST를 보낼 수 없다. 실제 확인은 Vercel 배포 후에 한다.

## 이번 범위에서 뺀 것

- 알림에서 특정 질문 바로 열기 (`QnA.jsx`의 화면 전환 구조를 먼저 손봐야 한다)
- 답변이 달렸을 때 학생에게 알림 (반대 방향. 필요해지면 같은 부품으로 붙인다)
- 공지사항·과제 등 다른 알림 (같은 부품 위에 얹을 수 있다)
- 야간 발송 제한 (지금은 언제든 바로 보낸다)
- 알림 발송 이력 저장 (실패를 추적할 필요가 생기면 그때 넣는다)
